Authentication vs Authorization :-

    Authentication :-
        It is a process of verifying the identity of the user's information, device before allowing to an application. It answer the fundamental question: "Who are you ?"
    
    Authorization :-
        It is a process of granting the users to access a specific services like the admin, super admin, user

        It answer the fundamental question :- "What can you do ?"

StateFull va StateLess :-

    StateFull :-
        The server remembers the client's past interactions and stores the session data locally on it's memory across multiple request 
    
    StateLess :-
        The server doesn't remembers the client's past interactions, it is completely independent, each and every request having it's required information to process it and responds to it

JWT :-

    JWT comes in 2015, JWT having the user's claims and it is stateless

    It is used to securely transmit the information between two parties in a json format

    The JWT are self contains, it is base64 encoded

        base64 :- series of characters, which combines the alphabets and numbers

    The JWT consist of 3 main parameters, 
        Header
        Payload
        Signature

        Header :- 
            Contains metadata specifying the token type (JWT) and the cryptographic signing algorithm (HS256)

            Cryptographic :-
                It is mathematical technique used to prove the authenticity of a digital data

        Payload :-  
            It contains the information about the user such as id, role, expiration time

        Signature :-
            Created by hashing the encoded header, encoded payload  and a secret private key to verify that the token is not altered

    Advantages :-
        StateLess
        Scalability

    DisAdvantages :-
        TokenTheft

Cookie :-
    Cookie is a someway of storing a piece of information, it can be any string. It is a one way of storing information

    In the context of backend authentication, cookies are a mechanism that allows servers to store specific pieces of information directly in a user's browser.

        How they work:

        Storage: Once a user successfully authenticates, the server sets a cookie containing an authorization token (such as a session ID or a JWT) in the browser.
        Persistence: A key feature of browsers is that they automatically include these cookies in all subsequent HTTP requests made to the same server.
        Automation: This process automates the task of sending and receiving tokens with every request, allowing the server to identify and authorize the user without requiring manual intervention from the client.
        Security Feature: Browsers ensure that a cookie set by one server is only accessible to that specific server, preventing other websites from accessing your data.

Types of Authentication :-

    There are two types of Authentication such as 
        1)stateful Authentication
        2)StateLess Authentication
        3)API key based Authentication
        4)OAuth 2.0

        StateFull Authentication :-

            How it works: After a successful login, the server generates a session ID and stores user data in a persistent store like Redis or a database. This ID is sent to the client via an HTTP-only cookie.

            Pros: Allows for centralized control and real-time session management, making it easier to revoke user access.
            Cons: Can face scalability challenges and increased operational complexity in distributed systems.

        Stateless Authentication

            How it works: The server generates a signed JWT (JSON Web Token) containing user information and sends it to the client. The server verifies the token using a secret key upon each request without needing a persistent session store.

            Pros: Highly scalable and ideal for distributed architectures since there is no dependency on a server-side session store.

            Cons: Token revocation is complex because the server does not track the state of individual tokens once they are issued.

        API key Based Authentication :-

            In the context of backend engineering, API key-based authentication serves a distinct purpose compared to stateful (session-based) and stateless (JWT-based) methods, which are typically designed for human-led, client-to-server interactions.

            How It Works
                API keys are unique, cryptographically random strings generated by a platform that allow for programmatic access to a server. Unlike user-facing login flows that require manual entry of credentials, API keys are used in machine-to-machine (M2M) communication.

                Mechanism: A user or developer generates the key in a UI. This key is then stored by the client (e.g., in an environment variable on a server) and attached to outgoing requests (often in headers) to identify the caller and grant access to specific server resources.
                Use Case: It is ideal for scenarios where one server needs to interact with another server’s capabilities programmatically without human intervention, such as integrating with a third-party service like OpenAI.

            Pros:
                Simplicity: They are easy to generate and manage for programmatic tasks (54:15).
                Automated Integration: They provide a clean, non-interactive way for systems to communicate without needing the complex, state-heavy, or human-trigger-based workflows required by sessions or JWTs.
            Cons:
                Security Risk: If a key is intercepted or leaked, the attacker gains direct access to the server’s capabilities.
                Management Overhead: Unlike standard user authentication, managing the lifecycle, permissions, and revocation of these keys requires dedicated administrative logic on the backend

        OAuth 2.0 :-

            OAuth 2.0 is a critical protocol used for authorization and delegation, allowing one platform to access resources from another on behalf of a user without sharing their password.

            Key takeaways about OAuth:

                Delegation Problem: It solved the security risk of sharing passwords when platforms need to communicate programmatically.
                Tokens: Instead of passwords, OAuth uses tokens with specific, limited permissions, which can be revoked independently.
                Roles: The flow involves the Resource Owner (the user), the Client (the requesting app), the Resource Server (the data host, e.g., Google), and the Authorization Server (the issuer of the token).
                Evolution to OIDC: While OAuth 2.0 handles authorization, it does not explicitly handle authentication (verifying who you are). OpenID Connect (OIDC) was built on top of OAuth 2.0 to add this identity layer using an ID Token (a JWT), enabling features like "Sign in with Google"


        What is the difference between OIDC and OAuth? :-

            The fundamental difference between OAuth 2.0 and OpenID Connect (OIDC) lies in their primary purpose within a system:

            OAuth 2.0 (Authorization): This protocol is designed for delegated access. It allows a third-party application to gain limited access to a user's resources on another platform (like Google or Facebook) without the user having to share their password. It focuses on answering the question: "What can this application do?"

            OpenID Connect (Authentication): Because OAuth 2.0 does not inherently verify the user's identity, OIDC was built as an identity layer on top of it. It introduces an ID Token (a JWT) that contains standardized user profile information. It focuses on answering the question: "Who is this user?"

            In short, OAuth handles permissions, while OIDC handles identity verification.

Security Best Practices :-

    Implementing robust security requires focusing on how authentication and authorization flows are handled to prevent vulnerabilities. Here are key security best practices discussed in the video:

    Authentication Security:

        Secure Password Storage: Never store passwords in plain text. Always use hashing algorithms to transform passwords into irreversible, fixed-length representations (10:00-11:27).
        Generic Error Messages: Avoid providing specific feedback like "user not found" or "incorrect password," as this helps attackers map out your system. Use generic error messages like "authentication failed" to keep attackers confused (128:03-130:17).
        Defend Against Timing Attacks: Attackers can infer if a username is correct by measuring how long the server takes to process the request. Use constant-time comparison functions or simulated response delays (like time.sleep) to ensure response times do not vary based on the input validity (130:33-135:28).
    General Best Practices:

        Use Managed Auth Providers: For production systems, avoid building your own authentication logic if possible. Using established Auth providers (like Auth0 or Clerk) shifts the burden of implementing complex, secure workflows to specialists (37:08-38:18).
        Principle of Least Privilege: Ensure users and services are only granted the permissions necessary for their specific tasks to limit the potential impact of a compromised account (123:31-125:49).
        Avoid Credential Sharing: Use OAuth 2.0 and tokens rather than sharing passwords when one service needs to access another, as this allows for granular, revocable permissions (101:15-107:44).

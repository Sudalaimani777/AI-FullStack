    2) Folder Structure :-

    node modules -> Have all the packages and the source code of the dependencies that we installed
    src -> Holds all the logic and UI files

    gitIgnore -> User to restrict the code that we don't wanna push it into the GitHub

    .next -> Automatically generated by Next.js. It stores compiled files,cache and build output required to run the application.We normally don't edit or push this folder to GitHub.

    app -> Holds the main application UI and routing structure of the Next.js application when using the App Router.

       page.tsx -> Defines the UI/page for a route
       layout.tsx -> Defines shared UI/layout for multiple pages
       loading.tsx -> Displays loading UI
       error.tsx -> Handles errors for a route
       not-found.tsx -> Displays the not-found page
       route.ts -> Used to create API Route Handlers
       globals.css -> Contains global CSS

    public -> Holds all the static files/assets that need to be directly accessible from the browser.

          Example:
              public/logo.png -> /logo.png

          It can contain:
              - Images
              - Icons
              - Fonts
              - PDFs
              - Videos
              - Other static files

    eslint.config.mjs -> Contains the configuration for ESLint. ESLint is used to check the code for potential errors, bad coding patterns and code-quality issues.

                     It helps us:
                         - Find unused variables
                         - Detect common coding mistakes
                         - Maintain code quality
                         - Follow coding rules and standards

    ESLint -> Checks your code
    eslint.config.mjs -> Tells ESLint what rules to follow

    next-env.d.ts -> Automatically generated by Next.js. It provides the TypeScript type information required by Next.js and helps TypeScript understand Next.js-specific types.We normally don't edit this file manually.

    next.config.ts -> Contains the configuration settings for Next.js. It is used to customize how Next.js behaves while developing, building and running the application. Simply Configuration of Next.js

                  It can be used to configure:
                      - Image settings
                      - Redirects
                      - Rewrites
                      - HTTP headers
                      - Other Next.js features and behavior

    package.json -> Contains the project information, dependencies and scripts required to manage and run the application.

                It contains:
                    - Project name and version
                    - Dependencies
                    - Development dependencies
                    - Scripts/commands

                Example:
                    npm run dev    -> Starts the development server
                    npm run build  -> Creates a production build
                    npm start      -> Starts the production server
                    npm run lint   -> Runs ESLint

    package-lock.json -> Stores the exact versions and dependency information installed by npm. It ensures that the same dependency versions are installed across different machines.It is automatically generated/updated by npm.We normally don't edit it manually.

            package.json
                ↓
    Defines required packages
                ↓
        package-lock.json
                ↓
    Locks exact dependency versions
                ↓
            npm install
                ↓
            node_modules/

    postcss.config.mjs -> Contains the configuration for PostCSS. PostCSS is used to process and transform CSS files and apply CSS-related plugins. postcss.config.mjs -> CSS processing configuration

                      It is commonly used with:
                          - Tailwind CSS
                          - Other PostCSS plugins

    tsconfig.json -> Contains the configuration settings for TypeScript. It
                 controls how TypeScript checks and handles the code
                 in the project.

                 It is used to configure:
                     - Type checking
                     - Strictness
                     - Module settings
                     - JSX settings
                     - Path aliases
                     - Which files TypeScript should include/exclude

CHAPTER 3 :- CLIENT AND SERVER COMPONENTS 

    Client Components :-
        1) There is a browser and the server

        2)The client sends the request to the server

        3)The server sends the static JS bundle, it has only the static data and it rendered and it takes some time.

            This is the First Contentful Paint for the client Components

        4)Again it send the API call to the server to fetch the actual data from the DB it takes some time to grab data and send it back to the browser

        5)Once all the data from the DB and collected by the browser it again re-rendered

        Overall in the Client Components the SEO is bad and also the UX is poor

    Server Components :-
        1)When the browser sends the request to the backend, instead of sending the static JS bundle it interact with the DB call happens first and sends the actual JS Business Logic bundle

        2)Then it does a thing called hydration, it is the process of making the DOM elements interactive by adding respective event 

            Like : Server sends UI -> Browser Displays it -> React connects JS and events to it

            Rendering = Creating the UI.

            Hydration = Making the already-rendered UI interactive.

            This is the First Contentful paint for the Server Components

            The First Contentful Paint is the time taken from the browser to load the content

            FCP = Time from page navigation until the first visible content appears.
        
        Overall in the Server Components, the SEO is great and the UX is good

    use client :-

        It is a directive, that tells the Next js "Treat this component as a client component"

        By default, components inside the app directory are Server Components.

            useState
            useEffect
            useContext
            onClick
            onChange
            window
            document
            localStorage

        If you need these, add:

            "use client";

        Important: "use client" does NOT mean "this only runs in the browser"

            This is a common misunderstanding.

            A Client Component can still be rendered on the server initially. "use client" mainly defines a client boundary—the component needs to be included in the client-side JavaScript so React can hydrate it and handle interactions.

        If the server component with the events, we can either use the "use client" in that component or we can use the "use client" in the parent component that we imported

CHAPTER 4 :- DATA FETCHING METHODS: SSR and SSG, getStaticPro

    Both are forms of server rendering.The fundamental difference is when the HTML is generated.

    SSG — Static Site Generation :-
        HTML is generated ahead of the user's request, traditionally at build time, and reused for requests. Modern Next.js can also statically render/revalidate content.

        Build / prerender
              ↓
          Generate HTML
              ↓
         Cache / CDN
              ↓
        User requests page
              ↓
        Existing result served

    SSR — Server-Side Rendering

        HTML is generated when the request happens.

            User requests page
                  ↓
           Server receives request
                  ↓
            Fetch current data
                  ↓
             Render HTML
                  ↓
             Send response

        SSG = prepare before the request.
        SSR = prepare during the request.

    |                         | SSG                     | SSR                        |
    | ----------------------- | ----------------------- | -------------------------- |
    | Rendering               | Ahead of request        | At request time            |
    | Data                    | Can be known ahead      | Needed at request time     |
    | Speed                   | Usually faster          | Usually slower             |
    | CDN caching             | Excellent               | More complicated           |
    | Freshness               | Depends on revalidation | Can be request-fresh       |
    | Server work per request | Lower                   | Higher                     |
    | SEO                     | Excellent               | Excellent                  |
    | Good for                | Blogs, docs, marketing  | Personalized/dynamic pages |

    next.config.ts :-

        logging: {
            fetches: {
                fullUrl: true
            }
        }

        logging.fetches.fullUrl

        It tells Next.js to show the complete URL of fetch() requests in the server console.

        Next.js can log information about that fetch, including the full URL.

        This is particularly useful when you're learning Next.js data fetching, caching, SSR, SSG, and revalidation, because you can see what requests Next.js is actually making.

    Revalidation :-

        const response = await fetch(
            `https://jsonplaceholder.typicode.com/posts/${slug}`,
                {
                    next: {
                     revalidate: 3600,
                    },
                }
            );

            What does revalidate: 3600 mean?
                3600 is seconds.
                Cache this fetched data and consider it stale after 1 hour.

            Next.js documents next.revalidate as the number of seconds after which a cached resource can be revalidated.

        Is this SSR or SSG?

            It's best understood as cached/static rendering with revalidation (ISR-style behavior), assuming the rest of the route doesn't introduce dynamic behavior.

        force-cache       → Cache
        revalidate: 3600   → Cache + refresh eligibility after 1 hour
        no-store          → Don't cache

        One nuance: revalidation does not mean the page is regenerated exactly at the 3600-second mark. It means the cached data becomes eligible to be refreshed after that period when the resource is requested again.

        | Key / Option                  | Example                                                       |                      Purpose                                                           |  When to use                                                                                      |
        | ----------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
        | `cache: "force-cache"`        | `fetch(url, { cache: "force-cache" })`                        | Stores and reuses the fetched response from the cache                                  | Data that rarely changes                                                                          |
        | `cache: "no-store"`           | `fetch(url, { cache: "no-store" })`                           | Fetches fresh data instead of using the persistent fetch cache                         | Frequently changing / request-specific data                                                       |
        | `next.revalidate`             | `fetch(url, { next: { revalidate: 3600 } })`                  | Caches the response and makes it eligible for revalidation after the specified seconds | Data that changes periodically                                                                    |
        | `next.tags`                   | `fetch(url, { next: { tags: ["posts"] } })`                   | Associates cached data with a tag so it can be invalidated on demand                   | When you want to refresh related cached data after a mutation                                     |
        | `next.revalidate + next.tags` | `fetch(url, { next: { revalidate: 3600, tags: ["posts"] } })` | Combines time-based and tag-based cache invalidation                                   | Production apps where data changes periodically but should also refresh immediately after updates |

CHAPTER 5 :- DATA FETCHING METHODS USING REACT QUERY, SSR, SSG


    1) DATA FETCHING


What is Data Fetching?

Data fetching means getting data from an API, database, or server.

Example:

const response = await fetch("https://api.example.com/users");
const users = await response.json();

Why?

Because applications usually need data from a backend/server.


2) CSR - CLIENT-SIDE RENDERING
------------------------------

What is CSR?

CSR means Client-Side Rendering.

The data is fetched in the browser after the page loads.

Example:

"use client";

import { useEffect, useState } from "react";

export default function Users() {

    const [users, setUsers] = useState([]);

    useEffect(() => {

        fetch("/api/users")
            .then(res => res.json())
            .then(data => setUsers(data));

    }, []);

    return <div>{users.length} users</div>;
}

Why use CSR?

- Data is mainly needed in the browser
- Highly interactive applications
- User-specific client-side data

Flow:

Browser
   ↓
Page loads
   ↓
useEffect()
   ↓
API request
   ↓
Data received
   ↓
UI updates


3) SSR - SERVER-SIDE RENDERING
------------------------------

What is SSR?

SSR means Server-Side Rendering.

The server fetches the data and renders the page for each request.

Example:

export default async function Users() {

    const response = await fetch(
        "https://api.example.com/users",
        {
            cache: "no-store"
        }
    );

    const users = await response.json();

    return <div>{users.length} users</div>;
}

Why use SSR?

Use SSR when the data needs to be fresh for every request.

Examples:

- User Dashboard
- Account Details
- Order Status
- Personalized Data
- Frequently changing data

Flow:

Browser
   ↓
Request
   ↓
Server
   ↓
Fetch Data
   ↓
Render Page
   ↓
Browser

Memory:

SSR = Request Time


4) SSG - STATIC SITE GENERATION
-------------------------------

What is SSG?

SSG means Static Site Generation.

The page is generated before the user requests it,
usually during the build process.

Example:

export default function About() {

    return <h1>About Us</h1>;

}

Why use SSG?

Use SSG when the data does not change frequently.

Examples:

- About Page
- Portfolio
- Documentation
- Blog
- Marketing Pages

Flow:

Build Time
   ↓
Generate Page
   ↓
User Requests Page
   ↓
Serve Page

Memory:

SSG = Build Time


5) ISR - INCREMENTAL STATIC REGENERATION
----------------------------------------

What is ISR?

ISR means Incremental Static Regeneration.

It combines static generation with periodic revalidation.

Example:

const response = await fetch(
    "https://api.example.com/posts",
    {
        next: {
            revalidate: 3600
        }
    }
);

3600 seconds = 1 hour

Why use ISR?

When data changes occasionally, but we don't need
a fresh API request for every visitor.

Examples:

- Blog
- News
- Product Catalog
- Documentation

Memory:

ISR = Static + Revalidate


6) REACT QUERY
--------------

What is React Query?

React Query is now called TanStack Query.

It is a library used to fetch and manage server data
in React applications.

It handles:

- Fetching
- Caching
- Loading
- Errors
- Refetching
- Mutations
- Query invalidation

Install:

npm install @tanstack/react-query

Why use React Query?

Without React Query, we manually manage:

- useEffect
- useState
- Loading
- Error
- Caching
- Refetching

React Query provides these features in a structured way.


7) QUERYCLIENT
--------------

What is QueryClient?

QueryClient manages React Query's queries and cache.

Example:

import {
    QueryClient,
    QueryClientProvider
} from "@tanstack/react-query";

const queryClient = new QueryClient();


8) QUERYCLIENTPROVIDER
----------------------

What is QueryClientProvider?

It provides the QueryClient to the React application.

Example:

<QueryClientProvider client={queryClient}>
    <App />
</QueryClientProvider>


9) useQuery()
-------------

What is useQuery()?

useQuery() is used to fetch/read server data.

Example:

"use client";

import { useQuery } from "@tanstack/react-query";

export default function Users() {

    const {
        data,
        isLoading
    } = useQuery({

        queryKey: ["users"],

        queryFn: async () => {

            const response = await fetch("/api/users");

            return response.json();

        }

    });

    if (isLoading) {
        return <p>Loading...</p>;
    }

    return <p>{data.length} users</p>;
}

Why use useQuery()?

It handles:

- Fetching
- Loading state
- Error state
- Caching
- Refetching


10) queryKey
------------

What is queryKey?

queryKey uniquely identifies a query.

Example:

queryKey: ["users"]

Another:

queryKey: ["products"]

Why?

React Query uses queryKey to identify and cache the data.

Example:

["users"]     → Users Cache

["products"]  → Products Cache


11) queryFn
-----------

What is queryFn?

queryFn is the function that actually fetches the data.

Example:

queryFn: async () => {

    const response = await fetch("/api/users");

    return response.json();

}

Memory:

queryKey = Which data?

queryFn = How to get the data?


12) isLoading
-------------

What is isLoading?

isLoading tells us whether the query is loading
its initial data.

Example:

const {
    data,
    isLoading
} = useQuery(...);

if (isLoading) {
    return <p>Loading...</p>;
}

Why?

To show a loading UI while data is being fetched.


13) isFetching
--------------

What is isFetching?

isFetching tells us whether a fetch operation
is currently happening.

It can happen during:

- Initial fetch
- Background refetch

Memory:

isLoading  = Initial loading

isFetching = Any active fetching


14) staleTime
-------------

What is staleTime?

staleTime determines how long the fetched data
is considered fresh.

Example:

useQuery({
    queryKey: ["users"],
    queryFn: fetchUsers,
    staleTime: 1000 * 60 * 5
});

Here:

5 minutes = Fresh

After 5 minutes = Stale

Why?

To avoid unnecessary refetching.


15) gcTime
----------

What is gcTime?

gcTime determines how long unused query data
can remain in the cache before garbage collection.

Example:

useQuery({
    queryKey: ["users"],
    queryFn: fetchUsers,
    gcTime: 1000 * 60 * 10
});

Memory:

staleTime = How long data is fresh?

gcTime = How long unused cache can stay?


16) useMutation()
-----------------

What is useMutation()?

useMutation() is used when we want to change
server-side data.

Usually:

POST
PUT
PATCH
DELETE

Example:

const mutation = useMutation({

    mutationFn: async (name: string) => {

        const response = await fetch("/api/users", {

            method: "POST",

            body: JSON.stringify({ name })

        });

        return response.json();

    }

});

Execute:

mutation.mutate("Sudalai");

Memory:

useQuery()    = Get data

useMutation() = Change data


17) QUERY INVALIDATION
----------------------

What is Query Invalidation?

It tells React Query that cached data may be outdated.

Example:

const queryClient = useQueryClient();

queryClient.invalidateQueries({
    queryKey: ["users"]
});

Example situation:

GET /users
    ↓
Users cached

POST /users
    ↓
New user created

Old cache may be outdated.

Therefore:

invalidateQueries(["users"])

The users data can then be refreshed.


18) SSR VS SSG
-------------

SSR:

Request
   ↓
Server fetches data
   ↓
Render page
   ↓
Response

SSG:

Build
   ↓
Fetch data
   ↓
Generate page
   ↓
User requests page
   ↓
Serve page


SSR = Request Time

SSG = Build Time


19) SSR VS SSG VS ISR
---------------------

SSR:

- Request-time rendering
- Fresh data
- Good for dynamic data

SSG:

- Build-time generation
- Very fast
- Good for static data

ISR:

- Static generation
- Periodic revalidation
- Good for data that changes occasionally


20) REACT QUERY VS SSR
---------------------

These are NOT the same thing.

SSR answers:

"Where/when should the page be rendered?"

React Query answers:

"How should client-side server data be fetched,
cached, refetched and updated?"


They can work together.

SSR
 +
React Query
